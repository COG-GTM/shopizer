# Shopizer 3.2.7 → Boot 3 operator upgrade and rollback

Scope: `origin/3.2.7` (Boot 2.5 / Java 11 / javax / H2 1.4.200) to
the AB-544 epic baseline (Boot 3.5.16 / Java 21 / Jakarta / H2 2.3.232).
This is not an assurance that the remaining epic tickets have shipped.
See [the cut-over ADR](../adr/0003-spring-boot-3-5-java-21-jakarta-cut-over.md),
[baseline tests](baseline-tests.md), and [ID generation](id-generation.md).

## Before the outage

* Require a **Java 21 runtime and build JDK**, plus Maven (system Maven used here;
  the wrapper now selects 3.9.9). Rebuild custom extensions against Jakarta APIs.
* Pin both old and new image digests/jars; retain old configuration, credentials,
  database engine binaries, and the complete CMS volume. Stop all writers before
  taking a consistent database + `files/` backup. Test restoring it independently.
* Do not rely on this branch's Dockerfile: it changed Java 11 to **17**, not 21,
  and copies the new MVStore seed instead of the old PageStore seed. Java 17
  cannot execute this Java 21 bytecode. A Java 21 deployment image is a release
  prerequisite (AB-547). GitHub CI now tests only JDK 21; CircleCI is unchanged.
* Do not replace a merchant database with the bundled demonstration seed.
  Inventory CMS objects and reconcile in-flight payments before the outage.

## H2 file conversion (offline, on a copy)

H2 2.x cannot directly open the 1.4 PageStore `.h2.db`. Keep the original file
and engine jar untouched. Example with `R=$HOME/ab549-rehearsal`, H2 jars from
the local Maven repository, and the demo user/password only:

```sh
H14=$HOME/.m2/repository/com/h2database/h2/1.4.200/h2-1.4.200.jar
H2=$HOME/.m2/repository/com/h2database/h2/2.3.232/h2-2.3.232.jar
java -cp "$H14" org.h2.tools.Script \
  -url "jdbc:h2:file:$R/backup/SALESMANAGER;IFEXISTS=TRUE" \
  -user test -password password -script "$R/export.sql"
# Review the export, then replace VARCHAR(2147483647) with CHARACTER LARGE OBJECT
# in a separate import.sql. Preserve quoted identifiers, especially "VALUE".
java -cp "$H2" org.h2.tools.RunScript \
  -url "jdbc:h2:file:$R/upgrade/SALESMANAGER" \
  -user test -password password -script "$R/import.sql"
```

1.4 SCRIPT exports can contain `VARCHAR(2147483647)`, beyond H2 2's VARCHAR
limit. The rehearsal changed only that type to CHARACTER LARGE OBJECT.
`VALUE` is reserved in H2 2: keep SCRIPT's double quotes; hand-written SQL
must quote this column. The new entity mappings explicitly quote it too.
Validate table counts, nulls, Unicode/large text, sequences and new entity IDs;
do not reset SM_SEQUENCER or substitute a pooled optimizer. H2 conversion is
**not in-place reversible**; rollback restores the old file, not the MVStore.

## CMS file stores: release blocker for existing tree layouts

AB-540 replaced TreeCache with string-keyed FlatCacheFiles while retaining
Infinispan 9.4.18 on this baseline. The stores include StoreRepository,
FilesRepository, and the intentionally misspelled DownlaodRepository `.dat`
files under `files/`. FlatCacheFiles uses path prefixes and encodes `%` and
`/` in file names as `%25` and `%2F`. A legacy tree `.dat` is **not** a flat store.
CacheManagerImpl fails startup with “stores using the removed Infinispan tree
layout must be migrated”; CacheManagerPersistenceTest covers this explicitly.

There is no AB-540 migration note or automated tree-to-flat converter in
`docs/upgrade/` at this revision. Do not invent a binary conversion or delete
production stores to get a green startup. Before cut-over, export all assets
through the old application's content APIs (including merchant/path/type and
filename metadata), import through the new application's content APIs into a
separate empty store, and compare inventories and retrieved bytes. A verified
deployment-specific export/import procedure is still required. Preserve the
original stores for rollback. Existing S3/GCP-backed content needs separate
provider verification; the local rehearsal does not cover it.

## Credentials and external integrations

* [AB-538 JWT notes](ab-538-jwt.md): `jwt.secret` must be Base64 encoding at least
  64 decoded bytes for HS512. Never deploy the public development key. Rotation
  invalidates old tokens; plan forced sign-in. Save the previous strong key for
  rollback, not merely the jar.
* [AB-539 integration rollout](ab-539-integration-sdks.md) and its
  [ADR](../adr/0001-integration-sdks-aws-v2-paypal-orders-v2.md): migrate each
  PayPal integrationKeys map to `clientId`/`clientSecret` from a REST app.
  NVP username/api/signature cannot be converted; old REST client/secret names
  also change. Select matching sandbox/live apps. Consumers must use PayPal's
  returned approval URL rather than constructing the old EC URL; after approval
  pass the order ID as paymentToken. Reconcile pending legacy transactions and
  retain previous module configuration securely for rollback. Verify authorize,
  capture, refund and payer approval with sandbox accounts before production.
* AWS SDK v2 uses DefaultCredentialsProvider for S3/SES. System properties now
  precede environment variables; avoid conflicting sources. Existing IAM roles,
  regions, buckets and permissions remain needed; no new app credential keys.
* [Canada Post port](canada-post-port.md) and
  [ADR](../adr/0001-canada-post-in-repo-jakarta-port.md): external starter replaced
  by in-repo Jakarta JAXB/RestTemplate implementation. Existing merchant Basic

  `module.shipping.canadapost.devUrl` are explicitly bound. Validate live/sandbox

## Start and smoke

Run outside the repository, never inside sm-shop. Supply a copied profile
database.properties in a loader directory. On Boot 3 the launcher package has
changed (the Boot 2 launcher below omits `.launch`):

```sh
cd "$R/upgrade"
/usr/lib/jvm/java-21-openjdk-amd64/bin/java \
  -Dloader.path="$R/upgrade/config" \
  -cp "$HOME/repos/shopizer/sm-shop/target/shopizer.jar" \
  org.springframework.boot.loader.launch.PropertiesLauncher --server.port=8081
# In another shell, after the startup completion message:
curl -fsS 'http://localhost:8081/api/v1/products?store=DEFAULT'
curl -fsS -H 'Content-Type: application/json' \
  -d '{"username":"admin@shopizer.com","password":"password"}' \
  http://localhost:8081/api/v1/private/login
curl -sS -o /dev/null -w '%{http_code} %{redirect_url}\n' http://localhost:8081/swagger-ui.html
curl -fsS http://localhost:8081/swagger-ui/index.html > /dev/null
curl -fsS http://localhost:8081/v3/api-docs > /dev/null
```

Use deployment credentials instead of demonstration credentials in production;
do not log returned tokens. Swagger UI's canonical path is now
`/swagger-ui/index.html`; `/swagger-ui.html` remains a redirect, not a removed
URL. OpenAPI is `/v3/api-docs`, replacing `/v2/api-docs`. Verify these behind your
actual proxy/context path too. Check catalog count, image/download retrieval,
authenticated admin operations, order creation, ID allocation and provider flows.

## Rollback procedure

1. Stop traffic and all new-version writers. Retain failed-upgrade logs and a
   separate snapshot for reconciliation. Never run old/new processes against the
   same embedded DB or CMS files concurrently.
2. Compare schema/DDL with the pre-upgrade snapshot. On MySQL, only reuse the
   current database if reviewed DDL and backward compatibility tests prove safe;
   otherwise restore the consistent DB backup. No production MySQL schema
   compatibility was executed in this rehearsal. Account for all post-cut-over
   writes: restoring a backup loses them unless explicitly reconciled.
3. Restore **both** the H2 1.4 `.h2.db` and the original `files/` tree together
   into a separate rollback directory, plus the old configuration/credentials.
   Do not rename an MVStore to `.h2.db`, or point the old engine at it. CMS flat
   writes and H2 conversion have no supported reverse conversion here.
4. Redeploy the pinned previous image/jar with its compatible Java runtime.
   For the old jar use Java 17 and
   `org.springframework.boot.loader.PropertiesLauncher`, with the rollback
   directory as working directory and its config directory as loader path.
5. Repeat products/login/old Swagger smoke, verify content byte comparisons and
   critical writes, then reopen traffic. Restore old PayPal config only after
   reconciling external transactions; provider-side operations cannot be undone
   by a database restore. JWT rotations may require another sign-in.

## Reproducible configuration-key audit

This scans dotted configuration namespaces in this document, not arbitrary
Java class names, filenames, dependency coordinates or URLs. PayPal map entries
are undotted and are documented in the linked AB-539 note. Search HEAD source
first, then the old tree for removed keys; exclude docs so this is not a
self-confirming check. Run from the repository root:

```sh
python3 - <<'PY'
import pathlib, re, subprocess
doc = pathlib.Path('docs/upgrade/3.x-to-boot3.md').read_text().split('## Reproducible configuration-key audit')[0]
keys = sorted(set(re.findall(r'\b(?:spring|springdoc|hibernate|jakarta\.persistence|logging\.level|db|jwt|module\.shipping)\.[A-Za-z0-9_.-]+', doc)))
keys = [key for key in keys if not key.endswith('.md')]
for key in keys:
    found = None
    refs = ('origin/3.2.7',) if key == 'spring.jpa.hibernate.use-new-id-generator-mappings' else ('HEAD', 'origin/3.2.7')
    for ref in refs:
        p = subprocess.run(['git', 'grep', '-F', '-l', key, ref, '--', 'sm-*', 'pom.xml'], capture_output=True, text=True)
        if p.returncode == 0:
            found = ref
            break
    print(f'{key}: {found or "MISSING"}')
    if found is None:
        raise SystemExit(1)
print(f'PASS: {len(keys)} configuration keys found')
PY
```
